## Renad – empty "Receiving custodian" dropdown

`renad_transfer_workspace()` lists custodians of the transfer's **receiving department**
(`transfer.receiving_department_id`), only for active users in **active** departments, and only
for transfers in `Approved`/`Scheduled` whose asset the signed-in custodian can send.
DEMO-IT already has an active custodian (Shaikha), so check the data with:

```sql
select t.transfer_status,
       sd.code as sending_dept, rd.code as receiving_dept, rd.is_active as receiving_dept_active,
       a.name  as asset,
       (select string_agg(u.full_name || ' (' || u.account_status || ')', ', ')
          from public.app_user u
          join public.user_role ur on ur.user_id = u.user_id
          join public.role r on r.role_id = ur.role_id
         where r.role_name = 'custodian' and u.department_id = t.receiving_department_id) as receiving_custodians
from public.transfer t
join public.department sd on sd.department_id = t.sending_department_id
join public.department rd on rd.department_id = t.receiving_department_id
join public.asset a on a.asset_id = t.asset_id;
```

- `receiving_dept` is not DEMO-IT → the request came from another department.
- `receiving_dept_active` = false → activate the department.
- `receiving_custodians` empty → add a fictional custodian to that department (Add user).
- All correct → sign in as a **custodian of the sending department** (e.g. DEMO-ENG for the printer).

Suggestion: add a fictional `custodian.it@demo.ku.ac.ae` for DEMO-IT instead of using a real student
account as demo data (NFR-SE08).
